# WordPress Abilities API vs. TYPO3 Capability Manifests

**Two registries that sound alike and solve opposite problems** — and why an installation wants both. Companion note to strategy item 19; compares the [WordPress Abilities API](https://developer.wordpress.org/apis/abilities-api/) (core 6.9, Nov 2025) with the approach in [TYPO3 Extension Security — Capability Manifests](https://www.webconsulting.at/en/blog/typo3-extension-security-emdash-capability-manifests) (`typo3-capability-manifest`).

Last updated: 2026-07-07.

---

## 1. The confusion worth clearing up

Both projects put a "registry of capabilities" at the center, and both were born from the same underlying fact: **a CMS is a pile of code whose actual behavior nobody can enumerate.** But they attack that fact from opposite directions:

- The **capability manifest** (webconsulting.at article, EmDash lineage) is **descriptive and inward-facing**: it declares what an installed *extension could do to the system* — which tables it writes, which hosts it calls, whether it XCLASSes core — so that admins, CI and policies can audit and gate the *supply chain*.
- The **Abilities API** (WordPress 6.9) is **prescriptive and outward-facing**: it declares what the *site offers to do for a caller* — named, typed, permissioned actions with JSON-Schema contracts — so that agents, REST clients and MCP adapters can *operate* the site through governed units instead of raw endpoints.

Shorthand: **manifests bound what code *may* do; abilities define what callers *can ask for*.** One is a security envelope, the other is an action surface.

## 2. Side by side

| Dimension | Capability manifests (`typo3-capability-manifest`) | WordPress Abilities API (core 6.9) |
|---|---|---|
| Unit of declaration | One **extension** (whole package) | One **action** (`namespace/ability-name`) |
| Direction | Inward: what this code could do *to* the system | Outward: what the site does *for* a caller |
| Registration | `Capabilities.yaml` shipped with the extension; can be **generated by static analysis** (nikic/php-parser) | `wp_register_ability()` at runtime with `label`, `description`, `category`, `input_schema`, `output_schema`, `execute_callback`, `permission_callback`, `meta.annotations` |
| Contract | Side-effect vocabulary (`database:write`, `network:outbound`, `mail:send`, …) + risk level + justification | Typed input/output **JSON Schemas** per action |
| Verification | **Audit**: declared vs. detected (AST scan); drift is flagged | **Execution pipeline**: validate input → check permission → execute → validate output |
| Enforcement point | Install/CI time (`capability:policy-check`: deny / review_required / max_risk_score) | Call time (permission callback per execution; `wp-abilities/v1` REST requires auth) |
| Primary consumer | Admins, security teams, CI pipelines | AI agents, the official **MCP Adapter**, REST clients, plugins |
| Failure it prevents | A rogue or compromised extension shipping undeclared behavior | An agent improvising against raw APIs without types, permission checks or annotations |
| What it cannot do | No runtime layer — a manifest never *executes* anything (the article's Phase 4, runtime monitoring, is future work) | Nothing about what plugin *code* may do — a WP plugin still runs with full process rights |

## 3. The asymmetry in each ecosystem

**WordPress shipped the action surface but still lacks the security envelope.** The webconsulting.at article's core stat — ~96% of WordPress vulnerabilities stem from plugins with full, undeclared process access — is *unchanged* by the Abilities API: abilities are opt-in units *on top of* plugins; the plugin underneath still reads any table and calls any host with no declarative permission model. WP fixed how agents talk to the site, not what plugins may do to it.

**TYPO3 (this lab) now has both halves, sharing one vocabulary.** `webconsulting/typo3-abilities` (strategy item 19, shipped 2026-07-07) deliberately reuses the manifest ecosystem's language:

- an ability's `sideEffects` use the **capability-manifest subsystem vocabulary** (`database:write`, `network:outbound`, …),
- its `riskTier` uses the **manifest risk levels and scores** (low 0 / medium 5 / high 10 / critical 15),
- its policy file (`config/abilities-policy.yaml`) mirrors **PolicyChecker semantics** (deny / review_required / max risk), extended with a human-in-the-loop approval flag,
- its scopes follow the sg_apicore `resource:operation` convention already used for API tokens.

So the two registries compose instead of competing: *the extension's manifest bounds the outer envelope; each ability declares which slice of that envelope one action uses; one policy language gates both.* An auditor can ask "does any ability claim a side effect its host extension never declared?" — a cross-check neither system can do alone, and a natural next audit rule.

## 4. Where each one closes the other's gap

- The manifests article concedes its main limit honestly: "declaration + auditing" has **no runtime enforcement**; Phase 4 (runtime monitoring middleware) is 2027 roadmap. For the **agent lane**, the abilities registry already *is* that runtime layer: agents never touch raw APIs, every call passes policy → validation → scopes → permission → execution → output validation, and since today every attempt (including denials) lands in `tx_abilities_trace`. Runtime enforcement for arbitrary PHP remains impossible in-process — but the surface agents use is fully gated.
- Conversely, abilities without manifests would rest on an unaudited foundation: the ability says "I write `tt_content`", but only the manifest audit verifies the *extension* doesn't also quietly write `be_users`. The envelope keeps the action surface honest.

## 5. The architecture lesson, restated

WordPress's real proof (Abilities API + official MCP Adapter) is **one registry, many protocol projections** — the MCP tool list is generated, never hand-rolled. The TYPO3 mirror does the same (compiler pass → `ability_*` MCP tools, CLI, REST planned) and adds what WP's registry lacks because the manifest ecosystem was there first: **scopes, risk tiers and side-effect declarations as first-class registry fields**, not just `readonly/destructive/idempotent` hints. WP annotations map 1:1 onto MCP tool hints; the TYPO3 registry *derives* those hints from richer governance metadata.

## 6. Takeaways

1. **Don't merge them.** Manifest = per-extension security envelope (audit/CI). Ability = per-action offer (runtime). Same vocabulary, different lifecycle, different consumer.
2. **The shared vocabulary is the moat.** Policy rules written once (`side-effect:network:outbound`, `risk:critical`) gate extension installs *and* agent executions.
3. **Pitch order for the article's audience:** manifests answer "can I trust what I installed?", abilities answer "can I let agents act here?" — enterprises currently budget for the second question, which funds the first.
4. **Upstream story (item 23):** WP proved a CMS core will accept an abilities registry; the TYPO3 proposal is stronger because it arrives *paired* with the supply-chain envelope WP still lacks.

## 7. What the lab actually did (2026-07-07)

The lab chose the **action surface** as the load-bearing layer and retired the standalone manifest tooling:

- `typo3-capability-manifest` and `api-capability-bridge` were **removed from the lab and archived read-only** on GitHub. Their two jobs were absorbed: the bridge's news auto-CRUD + `/studio/*` endpoints became **abilities** (news/pages/content/workspaces, defined in the desktop connector), and its backend-user-bound opaque token provider (`be_user_uid`) moved into the **sg_apicore fork** where `tx_apicore_token` actually lives — no bridge extension needed.
- The registry now serves **four projections of the same 18 abilities**, all verified live: CLI, MCP (`ability_*` tools), REST (`/api/abilities/v1/…` on the backend-user tokens), and the **TYPO3 Desktop Editor** (its news/pages/workspace operations delegate to the executor; the Electron app is unchanged on the wire).
- The **security-envelope half is not gone, it moved up a layer**: risk tiers, side-effect declarations and `deny`/`review_required` policy (now `config/abilities-policy.yaml`) are enforced at *execution* time on every surface, and `mcp-server`'s own internal `Capabilities.yaml` enforcement is untouched. What the lab dropped is the *static per-extension audit* CLI — the [capability-manifests article](https://www.webconsulting.at/en/blog/typo3-extension-security-emdash-capability-manifests) remains its record, and the audit approach is still valid for supply-chain review; it is simply not what gates *agent actions* here.

The pairing argument in §3 still holds in principle (an installation ideally wants both the CI-time envelope and the runtime surface); the lab's pragmatic call was that one governed runtime registry across four surfaces earns its keep first.
